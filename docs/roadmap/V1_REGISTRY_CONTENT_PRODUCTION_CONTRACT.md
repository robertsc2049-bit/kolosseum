Accepted as a content-governance slice.

Recorded at UTC: 2026-06-05T09:06:35Z

## Context

The v0 release lane is closed.

This slice defines the production contract for future v1 registry content work. It does not add registry content rows, exercise rows, equipment rows, substitution edges, programme templates, UI screens, database migrations, auth provider integration, billing, proof, export, package version changes, or release tags.

## Purpose

S22 defines how v1 registry content will be produced, reviewed, checked, and accepted before any active registry records are added.

The contract exists to stop content production from becoming ad hoc, claim-loaded, incomplete, or wider than v1.

## Locked v1 activities

All future v1 content production remains limited to:

- powerlifting
- general_strength
- rugby_union

No content slice may add, imply, seed, expose, copy, test, or document active support for another activity unless a later accepted decision record changes the locked set.

## Registry domains covered

- exercise_equipment_compatibility_registry

## Source classification

Every content item must be classified using one of these source classes:

- founder_domain_knowledge
- canonical_project_document
- public_rule_or_standard
- implementation_fixture
- copy_boundary_entry

Unclassified content is not allowed.

## Review status values

Allowed review status values:

- draft
- domain_reviewed
- copy_reviewed
- legally_bounded
- accepted

Only accepted content may become active registry content.

## Content execution status

Allowed content execution status values:

- inert_contract_only
- inert_content_draft
- active_registry_candidate
- active_registry_accepted

S22 itself must remain inert_contract_only.

## Deterministic id policy

Future content ids must be:

- lowercase
- snake_case
- stable
- human-readable
- domain-prefixed where useful
- independent of database row order
- independent of UI labels
- independent of timestamps
- independent of author initials

Content ids must not be regenerated by tooling unless a dedicated migration slice explicitly records the reason.

## Stable ordering policy

Future content lists must use explicit deterministic ordering keys.

Ordering must not depend on:

- file system order
- object insertion order
- database insertion order
- locale sorting without an explicit rule
- date of creation
- review author

## Required content-slice proof

Every future content slice must prove:

- all required fields are present
- all ids are deterministic
- all ordering keys are stable
- all records belong to locked v1 activities only
- all domain ids exist in the S21 scaffold
- all required fields match the S20 schema target
- all copy entries have copy/legal review state
- all claim wording checks pass
- all unsupported activity leakage checks pass
- no template execution path is introduced unless the slice is specifically accepted for template activation
- no UI screen is introduced
- no database migration is introduced unless separately accepted
- no package version is changed
- no release tag is created or moved
